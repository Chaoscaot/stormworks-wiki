1:# Force cap and remaining sensor questions
5:The four issue bodies and comments were read before analysis. Their snapshots are retained under `native/force-cap/`.
9:The cap uses a mass-derived assembly aggregate. It is not generally the mass of the body receiving the force, and it is not generally the sum of raw component and auxiliary mass getters. The normal connected-body case is decoded. The special immovable/root flags and connector edge cases remain qualified below.
13:`0x1404c88e0` builds the integer labels at assembly `+0x18`. It floods component links obtained through vtable slot `+0x60`, follows the counterpart at `+0x150` or `+0x148`, and finds its vehicle through component `+0x28`. This path does not test joint limits, lock input, relative motion or motor power. The RTTI-backed multibody class vtable `0x140b02a08` has `+0x60 = 0x1400cb6a0`, the identity getter, and `+0x68 = 0x14008fd10`, the null getter. Thus an ordinary multibody connection contributes to the same S group whether its joint can move or is locked. Winch class `0x140b958e8` also returns itself at `+0x60`. The flood has additional connector paths, described under remaining limits.
15:`0x1404be190` separately builds mass-redistribution groups through `0x1404bebe0` and `0x1404bec80`. That recursion follows a counterpart only if slot `+0x68` is null at both ends. Multibody links pass this test. Winches return themselves at `+0x68` and stop this recursion. These are distinct grouping rules. Do not call the temporary mass group the final S group.
19:For each temporary mass group, define `m_i` as vehicle `+0x72c` before adjustment. The builder zeroes it and, unless vehicle byte `+0x1478` is nonzero, sums component mass getter slot `+0x298` over list `+0x3f0`. Base getter `0x140328ea0` reads definition `+0x2b0`. Microprocessor override `0x140393b10` returns its integer dimensions at `+0x188` and `+0x18c` multiplied. This is a component mass sum, not a read of physics-body `+8`.
21:Auxiliary masses `e_j` come from component getters `+0x310` and their associated factor pointers from `+0x318`, when predicate slot `+0x308` is true. Wheel getter `0x1403a5cc0` copies definition mass to component `+0x148`; its factor pointer is `+0x14c`. Force emitter getter `0x14033d540` sets its auxiliary mass to 10 at `+0x298`, with factor at `+0x29c`. These auxiliary entries affect redistribution but are not directly added to the final S sum.
48:S has the executable's component-mass units because the operations are mass sums, ratios and dimensionless factors. The getter reads the definition mass value directly. This does not establish kilograms. For positive finite S, helper `0x1401a7ad0` limits vector magnitude to `k*S`; the k values retain the internal force-per-mass convention from the earlier reports. The helper does not integrate time.
52:- One body with component mass sum 1000 and no auxiliary mass has S=1000. An air-surface force of magnitude 8000 is capped at 5000. A jet/propeller cap is 100000 and a solid-rocket cap is 1000000.
53:- Two multibody-connected bodies with component sums 1000 and 1, no auxiliary mass, have `T=1001`, `H=1000`, `D=1025`, `r=1001/1025`. Their adjusted vehicle values are approximately 976.585366 and 24.414634. Both receive S=1001, whether the ordinary joint is free or locked. Each air-surface application has cap 5005. Applying one cap per component does not make that an assembly-wide total-force budget.
55:- Two separate label groups with masses 1000 and 1 receive S=1000 and S=1. They do not share a cap merely because both are present in the scene.

The name `locked-group-builder.asm` is only a file label; its decoded flood does not test lock state.

75:Definition `+0x2cc4` is tested at `0x1403ba806`, bytes `83 b8 c4 2c 00 00 01`, followed by `0x1403ba80d`, `0f 84 c9 00 00 00`, to `0x1403ba8dc`. 91:The rows above describe the matrix storage, not a promise of an Euler-angle convention. The type-1 stores are at `0x1403ba8ec..0x1403ba93a` and `0x1403ba969..0x1403ba9aa`. The type-1 `component+0x468` sign flip is `0x1403ba94b`, bytes `41 0f 57 c5`, after its field load at `0x1403ba942`. The ordinary branch loads the field at `0x1403ba879` and uses it directly. Zero angle makes both matrices identity, so this first branch alone does not establish the missile's zero-sweep forward axis.
99:Altimeter definition `rom/data/definitions/altimeter.xml` selects legacy gate 18. Linear speed selects gate 19. Their consumer is the same `0x1403c4d20` component evaluator. Gate 18 transforms the component grid position through physics state matrix `+0x18` using `0x14017a230`, then reads the resulting world Y coordinate. That helper explicitly adds matrix translation, including `matrix[13]` for Y. There is no terrain-height, seabed, wave-height, pressure or previous-position lookup in this case. The datum is world Y=0. The shipped description calls it metres above sea level. It is height above the fixed sea-level datum, not clearance over terrain or instantaneous wave surface.
101:The altimeter call is `0x1403c53a8`, bytes `e8 83 4e db ff`. The output is narrowed to float and set to zero if world Y exceeds 40000 or world X exceeds 156000. Those are one-sided comparisons, not absolute-value clamps. Constants are at `0x140bb0918`, bytes `00 40 1c 47`, and `0x140bb0610`, bytes `00 00 00 00 00 0b 03 41`. The native bounds are preserved here rather than interpreted as terrain behavior.
110:The read fields are state `+0x98` for linear velocity and `+0xa4` for angular velocity. `0x1403c5476`, bytes `e8 65 04 db ff`, calls the cross-product helper `0x1401758e0`; `0x1403c5489`, bytes `e8 22 07 db ff`, adds the linear velocity through `0x140175bb0`. There is no position-difference speed estimate or division by a sampling interval. The shipped output description specifies m/s.
112:Mode field `component+0x834` selects 0, full vector length; 1, signed projection onto the transformed configured sensor axis; 2, `sqrt(vx*vx+vz*vz)`; 3, `vy`; any other value, zero. The case also sets speed to zero above world Y=40000. Mode 1 obtains the axis from definition `+0x40`, combines the component rotation, and rotates it through the body transform. It does not subtract wind. The world transform with translation is used for altitude; the velocity lever arm uses rotation without translation through helper `0x140178e20`.

128:Here group is proxy `+8` and object_mask is proxy `+0xc`. The bit-12 test is `0x1400d9bf3`, bytes `0f ba e0 0c`. The intersections are `0x1400d9bf9`, `85 41 1c`, and `0x1400d9c01`, `85 41 18`. 136:The locator does not feed position or distance into noise helper `0x1401e3460`. At `0x1403c8603..0x1403c8625` it constructs periods 128 and 128, reads a shared counter through `0x1402b7af0`, passes that integer as X, passes Y=1, and passes a fourth argument zero. `0x1402b7af0` is exactly `mov eax,[rcx+4]; ret`. The helper converts the integer coordinates to float at `0x1401e3460..0x1401e346c`. This rules out independent per-beacon random draws and spatial position-dependent noise in this consumer. The same multiplier applies after the nearest-beacon maximum.

151:The native code evaluates the interpolation in float steps, so the reduced polynomial is not a claim about identical rounding. Instructions `0x1403c862a`, `f3 0f 59 05 0e 73 7e 00`, and `0x1403c8632`, `f3 0f 59 05 96 74 7e 00`, multiply by 1/128 and 0.1. Counter timing, large-counter precision, rollover and exact native numerical bounds are still open. For ordinary small nonnegative integer counter values, the reduced real-arithmetic model repeats every 128 counter steps. It is deterministic. `tools/model.py` retains the model and generated sample values. No runtime RNG was observed or invoked.
157:Producer gate 54 requires its enable input and the existing common active/power path. It obtains a registration through `0x1403cff80`, updates its world position, and writes registration byte `+0x14=1`. The disabled path writes that byte zero and calls `0x1408c8700` to clear its component handle. Gate 55 scans the shared beacon container at evaluator argument 16 `+0x98`. For each entry it obtains the registration through `0x1408b5d90`; the only per-entry test visible here is that the returned pointer is nonzero. It then reads position `+0x18`. It does not read registration `+0x14`, owner, frequency, line of sight or range in this loop.
159:The complete producer and consumer bytes are retained at `asm/logic-sensors.asm`, `0x1403c82e0..0x1403c86f0`. In particular, do not infer that merely toggling a byte immediately removes an entry from the container. Still open: registration ownership, the container's cleanup pass, exactly when disabled/destroyed registrations become null, which loaded/remote beacon producers populate the container, and the global simulation-mode branch's identity. This pass rules out extra range/channel/occlusion selection inside the locator loop. Issue #114 remains open for complete eligibility and native noise bounds/timing, while the noise input is now established as counter-based rather than spatial.
