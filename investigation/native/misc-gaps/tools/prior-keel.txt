All three sizes have the same lateral water-resistance law for equal body state, orientation and immersion. Definition mass changes the upright-force pair and a separate forward-velocity memory term. 9-## Evidence and notation
10-
11:All retained paths below are relative to `investigation/native/keel-windows/`. The main routine is `0x1403dfd20`, vtable `0x140b46518`, update slot `+0x358`. This identification and the air branch are inputs from [control-surfaces.md](control-surfaces.md). Normal cadence is 60 component updates per simulated second, established in [update-rate.md](update-rate.md).
12-
13-The reconstructed equations use real-number algebra. Native intermediate force values are mostly binary32. `tools/model.py` is not a bit-exact emulator. Force and mass are internal units; the conversion of editor mass labels to kilograms is not established here. World distances and speed use the existing physics-coordinate convention, metres and metres per second.
--
18-- `p` is the sampled component application point and `r=p-body_position`.
19-- `v=linear_velocity+cross(angular_velocity,r)` is the component point velocity. The water branch does not subtract wind or a sampled water-current vector. Its normal relative velocity therefore uses this body point velocity with water treated as stationary.
20:- `n` is `dynamic_side_axis` after deflection and component/body transforms. All three keel definitions set it to local X. The local deflection axis is Y. No normalization is added in this routine.
21:- `w=clamp(2*(0.25-(p.y-water_height)),0,1)`. The wave-surface query is `0x1402bbbb0`, called at `0x1403e0158`. The immersion interval is 0.5 metres, centred on the sampled water surface. All keel water work is skipped when `w<=0`.
22:- `K=min(S,4*m)`. The definition read and multiplication are at `0x1403e01e7`, bytes `f3 0f 10 83 b0 02 00 00`, followed by the multiply at `0x1403e01ef`. This is distinct from `M`.
23:- `h` is `component+0x180`, initialized to 1 at `0x1403df64e`, bytes `48 c7 83 80 01 00 00 00 00 80 3f`. Serialization routine `0x1403dfaa0` names it `keel_force_factor`, string at `0x140b6c940`. It scales the upright pair and memory force, not the main lateral resistance or fixed downward force.
24-
25:Application is conditional on global byte `0x140ceb6ff` and `component+0x178==0`. The existing normal-mode enable evidence is retained in `asm/normal-mode-enable.asm`. Computation alone is not evidence that a disabled or attached component applies its force.

27-## Lateral water force
--
40-`A` is `rudder_surface_area`. The factor 40 is only added for `rudder_type==2`. The generic water branch for other rudder types uses the same base law without that factor and with a different application limit. This is linear resistance in clamped normal velocity, not a quadratic drag law. The density-like coefficient is exactly `D*Q`; no water-density variable or extra factor 1000 is read in this branch. Assigning a physical density to these constants would be an inference.
41-
42:Every keel has `A=13`, so `Q=10`. For `M>=800`, `D=400` and `F_water_raw=-160000*w*n*clamp(dot(v,n),-50,50)`. Both clamps are important. The area field is already saturated for `A>=1/6`; actual voxel area and mesh dimensions are not read by this equation.
43-
44:`C` is helper `0x1401a7ad0`. The caller passes limit 100 for the keel at `0x1403e0590`, loading from `0x140bb0790`, data `00 00 c8 42`. The helper limits each call separately, uses `S`, replaces NaN coordinates with zero, and queues a force. It does not multiply by timestep. For a constant force and normal cadence, impulse per update is `F/60`.

100-## Forward-velocity memory
--
109-```
110-
111:This uses body linear velocity, not point velocity. The final force has world Y forced to zero. It does not multiply by `w` after the immersion gate. The filter is updated only while this branch runs. The coefficient load/multiply is `0x1403e0ade`, bytes `f3 0f 59 1d 26 ee 7c 00`, data at `0x140baf90c`, bytes `6f 12 03 3b`. The raw momentum force uses the embedded factor 4. Its queue call uses the same limit 100 as the upright pair.
112-
113-For a constant forward-speed step from zero and zero initial memory, the uncapped aligned force at update `j` is `-4*h*K*u_forward*0.998^j`. At 60 updates/s its mathematical decay time is about 8.325 simulated seconds. This decay is an inference from the native filter. It resists changes in forward velocity, not steady sideways sliding, and must not be added to a pure sideways-speed graph.

148-## Windows
--
150-`tools/resources.json` retains all 41 `window*.xml` definitions with numbered source lines and hashes. Every one uses `type="9"`, category 15. `tools/window-inventory.json` compares them with the other shipped definitions. There are no top-level attribute names unique to windows and no unique tag/attribute-name pairs anywhere in their definition text. The same type 9 is used by 18 non-window definitions: two linear modules, fourteen railing parts and two stair parts. A type-9 check alone is not a glass test.
151-
152:The factory at `0x14045dd20`, case 9, allocates 0xa8 bytes and installs vtable `0x140afe2a0`. The final installation is at `0x14045e005`, bytes `48 8d 0d 94 02 6a 00`, followed by the store to the object. A second factory at `0x1404b8f30` installs the same table at `0x1404b922a`, bytes `48 8d 0d 6f 50 64 00`. MSVC RTTI at `0x140cdb8e0` identifies `c_scene_vehicle_component_basic`. Slot `+0x30` points to `0x140373be0`, bytes `b8 09 00 00 00 c3`, which returns type 9. The complete 88-slot table, its bytes and comparison against block/base classes are retained in `tools/window-vtable-comparison.txt`.
153-
154:This basic table ends at slot `+0x2b8`; it has no extended component update slot `+0x358`. Slots `+0x38..+0x1f8` are the shared return stub `0x14008fd10`. Shared methods bind the definition pointer at `+0x58`, access definition geometry and perform generic component work. The only basic-versus-block differences are slot `+0x30` for the type return, `+0x40` for the block method versus a basic no-op, and `+0x208` for the definition-backed query. Neither the factory nor this table selects a window-specific class or update. Generic rendering and serialization methods still reach other code, so this is not a whole-program proof of no window behavior.
155-
156-Window geometry includes buoyancy data. For example, `window_1x1.xml` has one `flags="1"`, `physics_shape="0"` voxel and one buoyancy surface; `window_large.xml` has nine such voxels and nine buoyancy surfaces; `window_porthole.xml` has fifteen voxels and 46 buoyancy surfaces. `01_block.xml` uses the same voxel flags and shape for its single voxel and has six buoyancy surfaces. These resource observations rule out the assumption that transparent windows simply omit collision or buoyancy data. They do not establish how every shape seals a compartment or how damage modifies that data.
