7-## Answer in brief
8-
9:- Use **60 component updates per nominal simulated second** for active, normally simulated vehicles. The logic path calls the component dispatcher, then submits one physics interval. At `0x1407439c6` it sets the physics tick count to 1; at `0x1405e3aea` the worker divides that count by 60. The actual argument is `double(float(1)/float(60))`, approximately `0.01666666753590107` seconds.
10-- Component updates are outside the physics substep loop. The dispatcher at `0x1405498d6` calls virtual slot `+0x358` once for each component. The water, electric and modular-engine vtables resolve that slot to `0x1403ef860`, `0x1404008a0` and `0x140449670`.
11-- Rigid-body physics has a separate substep. The worker passes either `double(float(1)/physics_rate)` or the fallback `double(float(1/60))` to the physics solver. The coordinator contains 60, 120 and 180 settings. Those are solver rates, not three possible multipliers for the recovered component formulas.
12:- Both `server64.exe` and `server.exe` contain the same tick-count/60 call pattern. Shipped Lua code also converts a callback interval of N ticks to N/60 seconds.
13-- Multiply amounts per update by 60. For a constant relaxation fraction `k`, compound the recurrence: a gap retains `(1-k)^60` after one simulated second. This establishes simulation-time conversion, not a guarantee of 60 updates per wall-clock second under every load or game mode.

212-## Confidence and limits
213-
214:Confidence is high for the normal component-to-simulation-time conversion. The evidence links actual component vtables to one update pass, fixes the scheduled count to 1, follows it into a tick-count/60 argument, resolves the physics virtual target, and identifies the accumulator consuming that argument. Matching server code and the shipped Lua conversion corroborate it.
215-
216-Wall-clock scheduling is a different question. The threaded logic wrapper at `0x140844ff1-0x140844ffb` busy-waits until an integer millisecond timer has advanced at least 16 ms [stormworks64-wall-clock-worker.asm]. `0x140174f60` derives that timer from nanoseconds divided by 1,000,000 [stormworks64-clock-ms.asm]. This is not a `dt=0.016` physics call and does not establish a 62.5 Hz simulation unit. The outer scheduler's complete pacing policy was not recovered. Report rates as per simulated second, and do not promise an exact wall-clock rate under overload, pause or network catch-up.
217-
218:Sleep/fast-forward and inactive vehicles are also outside the normal-rate conversion. The embedded addon documentation says `game_ticks` is normally 1 and can be 400 while sleeping [tables.txt]. That is not evidence that every component gets 400 calls. No such extrapolation is made here. The physics-detail flag's name, arbitrary rate override limits and all multiplayer synchronization paths remain untraced.
219-
220-No in-game measurement is needed to settle the nominal dt. If a future task needs wall-clock throughput, the minimal additional check is to count 3600 microcontroller `onTick` calls in an active vehicle and compare the interval with a stopwatch at full simulation speed, then repeat under load. That would measure real-time throughput, not change the recovered per-update formulas or establish sleeping behavior.
