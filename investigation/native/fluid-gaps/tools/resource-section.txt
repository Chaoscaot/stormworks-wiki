136:## #152. Base fuel inventory transfers
137-
138-The issue links to mechanics/resource-storage rather than a component family. Its source is `rom/data/missions/default_resource_storage/script.lua`, retained with line numbers in `tools/resources.txt`.
139-
140-Lines 40..47 increment a local callback counter once per `onTick` call, wrap at 60 and process a port when `port.id % 60 == tick`. The `game_ticks` argument is not used. A particular port is therefore eligible once every 60 callbacks, not once per callback and not necessarily once per wall-clock second. This source does not establish the engine's callback scheduling policy or how catch-up ticks affect it.
141-
142-On an eligible callback:
143-
144-- Diesel input adds the complete `tank_data.values[1]` to tile diesel inventory when total tank value is positive, then requests zero fresh water and zero nitrogen in the inlet. Jet input analogously adds `values[2]` to jet inventory. There is no constant per-callback litre cap. See lines 52..68.
145-- Diesel output computes `delta=min(capacity-total_value, tile_diesel_stock)`. If delta>0, it subtracts delta from the tile, requests `old_total+delta` of the tank's existing `fluid_type`, then requests zero nitrogen. Jet output does the same with tile jet stock. The preceding capacity guard uses the target species entry, but delta uses total value. See lines 71..96.
146-- The addon does not check setter return values or establish atomicity between tile and vehicle writes. Tile inventory changes are submitted later when `is_update` is true. Processing the input before the output permits the newly credited tile stock to feed an output in the same callback.
147-
148-Worked pure-fluid arithmetic example: an outlet of capacity 100 L and old total 40 L with 25 L tile stock requests a 65 L tank and leaves zero tile stock. If the native setter applies those requests exactly and the old dominant fluid matches the intended fuel, arithmetic stock is 65 L both before and after. That conservation statement is conditional. The addon itself does not prove its native preconditions.
149-
150-Mixed-fluid counterexample at the request level: a nominal diesel outlet dominated by jet fuel retains `tank_data.fluid_type` in the setter request. The code does not force fluid ID 1. It can debit diesel tile stock while requesting an increase of the old dominant species. An inlet credits only the selected fuel entry but requests clearing fresh water and nitrogen, not explicitly clearing that credited species. This rules out deriving unconditional species conservation merely from equal-looking scalar additions and subtractions. It does not prove the eventual game state without the native application semantics.
151-
152-The native bridge is partly traced. Registry entries at `0x14059a9f3..0x14059aa24` bind `setVehicleTank` to `0x1405b1cc0` and `getVehicleTank` to `0x1405b2140`. Their virtual calls use `c_script_operators` vtable `0x140b11a28`. Slot +0x3e0 selects named setter `0x140730ea0`; slot +0x2f8 selects named getter `0x140733a30`. The setter resolves the named component, then calls slot +0x3d8, `0x140730f50`.
153-
154-`0x140730f50` appends a 36-byte request to the queue at operators.service+0x1f0. It stores the vehicle ID, voxel position, requested value, fluid ID and request kind 2. It does not directly edit the tank's species array. The getter resolves a named component and invokes its +0x498 serializer. Water-component serializer `0x1403f9e40` is retained as a downstream example, including its volume conversion and jump-table boundary. It is not a proof of setter behavior.
155-
156-Still open, exactly: the consumer of request kind 2, its clamping/replacement/additive semantics, ordering of two requests against one tank, handling of zero nitrogen and mixed fluids, stale reads between callback and application, and failure behavior were not recovered. The addon and queue writer rule out an immediate synchronous tank assignment at the Lua bridge, a fixed litre/callback cap in the addon, and a callback-time guarantee derived from unused `game_ticks`. They do not rule out conservation in a particular pure-fluid runtime setup. No wall-clock callback cadence was measured or inferred from the unrelated component 60 Hz rate. A runtime test remains necessary unless that native consumer and callback scheduler are decoded.
