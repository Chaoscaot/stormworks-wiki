152:## Follow-up, item 2: meteor shower spawn and impact
154:Native shower operator `0x140726580` clamps magnitude M to [0,1]. It sends one main meteor per recipient, size `max(1,20*M)`, position `target - 30000*d`, velocity `20*d`, where d is the normalized randomized incoming direction. It additionally sends `trunc(10*M)` secondary meteors per recipient. Each secondary aims at independent horizontal offsets in [-500*M,500*M], starts a distance `20000 + U*15000*M` back along d, has size `max(1,(0.1+0.3*U)*20*M)`, and velocity `(19+U)*d`. Each U denotes a separate native random draw `(rand()&32767)/32767`. The per-recipient loops send copies of the same shower, not additional meteors in one client's world. For the shipped M=1 call this is one size-20 meteor and ten size-2-to-8 meteors. Secondary size and speed are drawn inside the recipient loop, so copies need not be identical.
158:Byte anchors in `followup/meteor-shower-spawn.asm`: `0x140726754`, `f3 44 0f 10 25 6b 9f 48 00`, loads 20; `0x14072693b`, `f3 0f 59 05 09 9d 48 00`, multiplies M by 10; `0x140726943`, `f3 48 0f 2c c0`, truncates the count. `followup/meteor-constants.txt` retains the address, bytes and float32 value of each referenced constant. Event 113 dispatch at `0x14085f718`, bytes `e8 f3 df f1 ff`, reaches `0x14077d710`, which appends a meteor to scene+0xbb1a8 and copies position, velocity, size and flag. `followup/meteor-update.asm` and the scene pseudocode retain the integration and land/water impact branches. Impact sends event 114 with position, size and flag, then removes the meteor.
162:The shared explosion update `0x140593ec0` advances age by float32 0.0166599992663 and radius R by `R=343*age`. Its record+0x24 becomes `initial_amplitude*(1-clamp(R/(250*strength),0,1))`. Byte anchors `0x14059417c`, `f3 0f 59 35 7c c6 61 00`, and `0x1405941be`, `f3 0f 11 46 24`, establish radius growth and the amplitude store. The 250 coefficient is at `0x140bb07e8`, bytes `00 00 7a 43`. This amplitude reaches zero at 250*strength, 2500 m for strength 10. It is not a proven block-damage cutoff. In particular body impulse helper `0x140594620` independently applies `min(500000*strength/R,30000*body_mass)` in a shell `(max(0,R-5.714379787))² < distance² < R²`; that expression does not read record+0x24. Tree processing has its own R<20*strength gate. The record also has a 270-count lifetime. Do not extend one of these gates to every consumer.
164:Still open: final block/voxel damage, occlusion and HP falloff; the maximum radius of every explosion consumer; and the ocean-event reach from the true-flag main. Ruled out equating meteor size, particle bounds, the 250*strength amplitude boundary or tree processing range with a universal radius beyond which nothing happens. `followup/explosion-*.asm`, `followup/explosion-constants.txt` and the named function pseudocode retain the distinct paths. `0x14073f890` contains a local-character explosion observer and sound/notification handling, not a demonstrated final voxel-damage equation.

184:The shipped forest-fire addon only receives objectives. Native tree ignition is `0x140559870`. 190:Spread selection offsets the source point by `5*manager_vector[+0x70,+0x78,+0x80]`, then searches eligible zero-intensity trees with horizontal squared distance strictly below 100. It chooses one and calls `0x140559870` with initial intensity 1. The vertical chunk test is separate. Thus 10 m is a search radius about an offset point, not a universal fire safe radius. Failed spread sets state flag bit 2, suppressing this tree's further attempts in this branch. `0x14055ce00`, bytes `f3 0f 10 15 88 39 65 00`, loads 100 for squared-distance selection; `0x14055cf5d`, bytes `e8 0e c9 ff ff`, calls ignition. `followup/forest-fire-update.asm`, `forest-spread-target.asm` and the named pseudocode retain the tests. Manager update writes the offset vector using sampled horizontal weather wind; its exact magnitude conversion has not been reduced here.
